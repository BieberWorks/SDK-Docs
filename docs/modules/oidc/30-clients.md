# Clients

A client is an application that signs users in through the provider. There are two kinds, told apart by their **source**:

| Source | Created by | Changed by | Notes |
|---|---|---|---|
| `Configuration` | `Oidc:Clients`, seeded at every host start | the configuration only | Read-only for the administration facade and the admin API (HTTP 409 `Oidc.ClientReadOnly`). |
| `Admin` | `IOidcClientAdmin` / the admin API | the same | The seeder never touches them. A configured client whose id collides with an administered one stops the start with a clear message. |

Seeding is idempotent: it creates missing configured clients and updates existing ones to match the configuration. Clients that are
removed from the configuration are **not** deleted; delete them through the facade (only `Admin` clients) or the database.

## Configured clients

| Key | Meaning |
|---|---|
| `ClientId` | Unique id. |
| `DisplayName` | Optional; defaults to the id. At most 100 characters. |
| `Type` | `Confidential` (default, needs a secret) or `Public` (no secret, PKCE only). |
| `ClientSecretFile` | Path of a secret file. The secret is never part of the configuration; the database stores only a hash (OpenIddict's PBKDF2 hashing). A secret that still matches is left untouched; a changed file rotates the secret at the next start. |
| `RedirectUris` | Exact matches only. No wildcards, no fragments; https, or http for `localhost`/loopback. Case, trailing slash and query differences do not match. |
| `PostLogoutRedirectUris` | Exact matches; used by [end-session](./10-usage.md#signing-out-at-the-provider). The end-session permission is granted automatically (existing administered clients get it once at startup). |
| `ConsentType` | `Implicit` (default) or `Explicit`, see [Consent](#consent). |
| `Scopes` | Scopes the client may request. Empty or omitted means the defaults `openid profile email`, applied when the client is seeded. A list you give is used as written and must contain `openid`, so a configured client can have fewer scopes (`["openid"]`) or more. `offline_access` enables refresh tokens. |
| `Audiences` | Audiences of the client's access tokens; empty means `Oidc:DefaultAudiences`. |

Every client requires PKCE. Client authentication at the token endpoint: `client_secret_basic` and `client_secret_post`.

```json
"Oidc": {
  "Clients": [
    { "ClientId": "grafana", "Type": "Confidential", "ClientSecretFile": "/run/secrets/grafana_client_secret",
      "ConsentType": "Implicit", "RedirectUris": [ "https://grafana.example.org/login/generic_oauth" ] },
    { "ClientId": "partner-portal", "Type": "Confidential", "ClientSecretFile": "/run/secrets/partner_client_secret",
      "ConsentType": "Explicit", "RedirectUris": [ "https://portal.partner.example/callback" ] }
  ]
}
```

## Consent

| `ConsentType` | Behavior | Use for |
|---|---|---|
| `Implicit` | No consent page. The user is redirected back as soon as there is a session. `prompt=consent` is ignored. | Your own first-party applications. |
| `Explicit` | The user decides once per client and scope set. The decision is stored as a permanent authorization; later requests with the same or fewer scopes skip the page, a request for an additional scope asks again. `prompt=consent` forces the page, `prompt=none` without a stored decision answers `consent_required`. | Anything you do not fully own. |

Flow with explicit consent: authorize, sign in if needed, redirect to `Oidc:ConsentPath` (default `/connect/consent`) with
`?returnUrl=<the authorize request>`, the user presses Accept or Deny, and the page posts a plain HTML form to `/connect/authorize`.
Accept issues the code. Deny answers `error=access_denied` with the `state` of the relying party. The decision of one user never
applies to another. The form carries an antiforgery token; a post without a valid one is answered with 400 and changes nothing, and
the provider validates client, redirect URI, PKCE and scopes again on that post, so a manipulated form cannot reach a foreign redirect URI.

The consent page names the signed-in user (display name and e-mail address taken from the user principal, for example
`Ada Lovelace (ada@example.org)`), so the user sees which account is about to grant access. Nothing is shown when the host has no
authentication state.

## Client administration

`IOidcClientAdmin` (in `Oidc.Contracts`) is the one interface for managing administered clients: `ListAsync`, `GetAsync`,
`CreateAsync`, `UpdateAsync`, `RotateSecretAsync`, `DeleteAsync`, `GetAvailableScopesAsync`. All of them return `Result` values with
stable error codes (`OidcErrorCodes`). The implementation in `BieberWorks.SDK.Oidc` checks the permission `oidc:clients:manage` of
the acting user itself (read live from the user store on every call, not from token claims), so the facade is safe to call from any code path, not only from a page or an endpoint.

- A client secret is generated by the server (32 random bytes), stored only as a hash and returned **once**, in the result of create
  and rotate. Rotation invalidates the old secret at once. List, detail and update never contain a secret.
- Client id and type cannot be changed after creation.
- Changes are published as audit events (`OidcClient*Event`, `OidcConsent*Event`; never with a secret). The module itself does not
  persist them: a host with an audit module stores them, a host without one only logs the operation.

### Rules for administered clients

Clients created through the facade or the admin API are validated on the server, whatever the caller (UI, API or code) checks beforehand:

- The client id matches `^[a-z0-9][a-z0-9._-]{2,63}$` and is not the reserved id `new` (the route of the "new client" page).
  Violations give `Oidc.ClientIdInvalid`.
- A blank display name falls back to the client id; a name longer than 100 characters gives `Oidc.DisplayNameInvalid`.
- At least one redirect URI, each absolute, without fragment or wildcard, https (http only for loopback). Violations give `Oidc.RedirectUriInvalid`.
- Scopes come from `GetAvailableScopesAsync` and contain `openid`. Violations give `Oidc.ScopeInvalid`.
- A request body that is missing or not valid JSON gives `Oidc.RequestInvalid` (HTTP 400) from the admin API.

The error codes are stable; `Oidc.Client` maps every code of the API back to the same error, so callers handle the same code in
process and over HTTP. New codes are additive: existing codes and the JSON wire format do not change.

### Admin API

Mapped by the `Oidc` module (`IEndpointModule`) under `/api/v1/oidc` **only when `Oidc:AdminApi:Enabled` is `true`** (default `false`; otherwise 404):

| Method and path | Purpose | Answer |
|---|---|---|
| `GET /clients` | List | `OidcClientSummary[]` |
| `GET /clients/{clientId}` | Detail | `OidcClientDetail`, 404 if unknown |
| `POST /clients` | Create | 201, `{ client, secret }` (secret for confidential clients only, once) |
| `PUT /clients/{clientId}` | Change | `OidcClientDetail`; 409 for a configured client |
| `POST /clients/{clientId}/secret/rotate` | New secret | `{ client, secret }` (once) |
| `DELETE /clients/{clientId}` | Delete | 204 |
| `GET /scopes` | Scopes a client may be given | `string[]` |

Rules: **bearer tokens only** (a session cookie is answered with 401, so the API cannot be driven from a browser session);
the scope `identity.admin` in the access token **and** the permission `oidc:clients:manage`, which is read live from the user store
(enforced on the whole route group, see [Security](40-security.md#client-administration-api));
401 without a token, 403 without the permission or without the scope; errors are `ProblemDetails` with `code` set to the error code and status 400, 403,
404 or 409; every answer is `Cache-Control: no-store`. The routes are **not** for the public internet: they return secrets in
clear text. Publish them only on an internal network or behind an internal proxy router, and prefer a TLS hop to the service.

### Access token requirements

- The access token must carry the scope `Oidc:AdminApi:RequiredScope` (default `identity.admin`; claim `scope`, `scp` or `oi_scp`,
  compared case-sensitively). A token without any scope claim (for example one from the old login `/api/auth/login`, or a service token),
  a token that only has `openid roles` and a token with only the former scope `perm` answer **403**, even when its user is an
  administrator. A session cookie stays 401. Add `identity.admin` to the scopes of the client that signs the administrator in.
- `Oidc:AdminApi:AllowedClients` (list of client ids, default empty) restricts the API to tokens issued to those clients. The client is read
  from the claim `client_id`, else `azp`; a token without a client claim, or with two different values, is refused with 403. Empty means every
  client that is allowed the required scope may call the API for an administrator, and the provider logs a warning at start. The list is read
  once when the routes are mapped: **a change needs a restart**. Entries must be non-empty, free of whitespace, at most 100 characters and unique.
- The permission is not taken from the token: a removed role, a locked or a deleted administrator is refused with the next request.

```json
{ "Oidc": { "AdminApi": { "Enabled": true, "AllowedClients": [ "admin-shell" ] } } }
```

Service-account tokens (`/api/v1/auth/service-token`) do not satisfy the policy in this version; the caller is a signed-in user with
the permission (for example an administrator signing in to an admin console with the client scope `identity.admin`).

### Calling the API from another host: `Oidc.Client`

`BieberWorks.SDK.Oidc.Client` implements `IOidcClientAdmin` over the admin API, with the same results and error codes as the in-process
implementation. It references only `Oidc.Contracts`.

```csharp
services.AddOidcAdminClient(o => o.BaseAddress = new Uri("https://identity.internal:8443/"));
services.AddScoped<IOidcAdminTokenSource, SignedInUserTokenSource>();   // you supply the source, there is no default
```

`IOidcAdminTokenSource.GetAccessTokenAsync` returns the bearer token for the current call (or `null`, which the client reports as an
unauthenticated failure). The source is replaceable: the access token of the signed-in user (scope `identity.admin`) is the supported case today; a
service-account source can be plugged in later without touching the client or the UI. Tokens and secrets are never logged. A timeout or
an unreachable provider becomes an `Unavailable` error, not an exception.

## Choosing packages per host

| Host | Packages | Why |
|---|---|---|
| Identity provider host (login and consent) | `BieberWorks.SDK.Oidc` + `Oidc.Consent.UI.Blazor.MudBlazor` (or `Oidc.Consent.UI.Blazor` plus your own markup) | The consent page needs `IOidcConsentReader` and the authorize endpoint of the implementation. There is **no HTTP replacement**; the module refuses to start without `Oidc` and says so. |
| Admin console (separate host) | `Oidc.Admin.UI.Blazor.MudBlazor` + `Oidc.Client` | The administration UI needs only `IOidcClientAdmin`: over HTTP from `Oidc.Client`, or in process when the host also runs `Oidc`. |
| Host that does both | `Oidc` + both UI packages | `Oidc` provides `IOidcClientAdmin` in process; no `Oidc.Client` needed. |
| Host with its own UI | `Oidc` only | Everything works without any UI package, see below. |
| Resource server | none of these | Validates access tokens against the JWKS. |

The two UI package families do not reference each other, so a provider host does not get routable administration pages and an admin
console does not get a consent page. The administration pages are `/admin/oidc/clients` and need the permission `oidc:clients:manage`.

## Custom login/consent UI

The provider needs two pages from its host: sign in and consent. Sign-in belongs to Auth (`/auth/login` and friends, which a host can
replace with its own pages at the same paths). For consent:

1. Set `Oidc:ConsentPath` to a local path of your page (a single leading `/`, no query, fragment or backslash; anything else stops the start).
2. Build the page on **`ConsentPageBase`** (package `Oidc.Consent.UI.Blazor`), which reads `returnUrl`, loads the display data and exposes
   `ClientName`, `ScopeItems`, `FormFields`, `FormAction`, `AcceptName` and `DenyName`. You write only the markup; or
3. build it without any Oidc UI package from `IOidcConsentReader.GetAsync(clientId, scopes)` (display data only).

Either way the page must post a plain HTML form (`method="post"`) to `/connect/authorize` containing all original authorize parameters
as hidden inputs (`client_id`, `redirect_uri`, `response_type`, `scope`, `state`, `nonce`, `code_challenge`, `code_challenge_method`,
`prompt`, `max_age`, `login_hint`, `ui_locales`, as present in `returnUrl`), the antiforgery token (`<AntiforgeryToken />`,
field `__RequestVerificationToken`) and one submit button named `submit.Accept` or `submit.Deny`. Do not decide anything in a Blazor
circuit and do not trust `returnUrl`: it only fills the form, the provider validates everything again on the post. The page must be
served `Cache-Control: no-store` and must not be frameable. If the page comes from a package that the host filters by route (the
Identity image filters by an allowlist), add its route to that list.
